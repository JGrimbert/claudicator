## Plan — Auto-chargement des tasks créées depuis une issue

### 1. Analyse du problème

Deux bugs distincts, liés :

**Bug A — Pas d'auto-sélection après création**
Quand `createTasksForIssues()` ou `createTasks()` crée des tasks depuis `IssueAnalysis.svelte`, il appelle `notifyTaskCreated()` qui incrémente `taskRefreshTick`. Cela déclenche `onRefreshTick()` dans `TaskList.svelte`, qui rafraîchit la liste silencieusement — mais **ne sélectionne aucune task**. L'utilisateur doit cliquer manuellement.

**Bug B — Task bloquée à "Chargement..." au clic**
Dans `TaskList.svelte:selectTask()` (ligne 303–312), lorsqu'une task a un `issueNumber`, le code fait :
```ts
agentState.update(s => ({ ...s, status: "loading" }));
const res = await fetch(`/api/issue?number=${task.issueNumber}`);
const full = await res.json();
agentState.update(s => ({ ...s, status: "idle" }));
```
Il n'y a **aucun try/catch** autour de ce fetch. Si la requête échoue ou lève une exception, `agentState.status` reste figé à `"loading"`. Tous les composants qui lisent ce statut (notamment `IssueList`) restent bloqués à "Chargement...".

### 3. Stratégie

**Bug A — Store d'auto-sélection**

Ajouter dans `stores/agent.ts` un store `autoSelectIssueNumber: writable<number | null>(null)`.

Après la création de tasks dans `IssueAnalysis.svelte`, alimenter ce store avec le premier `issueNumber` nouvellement créé (pas les existants). Dans `onRefreshTick()` de `TaskList.svelte`, si ce store contient un numéro, chercher la task correspondante dans la liste fraîchement chargée et appeler `selectTask()` sur elle. Remettre immédiatement le store à `null` pour éviter les boucles.

Cela évite toute prop drilling ou refactoring majeur — le store est le canal de communication entre `IssueAnalysis` et `TaskList`.

**Bug B — Try/catch autour du fetch issue**

Envelopper la section `if (task.issueNumber)` dans un `try/catch`. En cas d'erreur, remettre `agentState.status` à `"idle"` pour débloquer l'interface.

  - Chercher dans `tasks` la task dont `issueNumber === $autoSelectIssueNumber`
  - Si trouvée et que `selected?.id !== task.id` : appeler `selectTask(task)`
  - Remettre `autoSelectIssueNumber.set(null)` immédiatement (avant l'await de selectTask)
- Dans `selectTask()` (ligne 303–312), envelopper le bloc `if (task.issueNumber)` dans un `try/catch` :
  ```ts
  if (task.issueNumber) {
      try {
          agentState.update(s => ({ ...s, status: "loading", plan: null }));
          const res = await fetch(`/api/issue?number=${task.issueNumber}`);
          const full = await res.json();
          agentState.update(s => ({ ...s, issue: full, status: "idle", ... }));
      } catch {
          agentState.update(s => ({ ...s, status: "idle" }));
      }
  }
  ```

### 5. Vérifications et nettoyage final

- **Anti-boucle** : `autoSelectIssueNumber` est remis à `null` AVANT l'appel async à `selectTask()`, donc si `taskRefreshTick` se déclenche à nouveau, le store est déjà vide.
- **Sélection déjà active** : vérifier `selected?.id !== task.id` avant de re-sélectionner, pour ne pas relancer un chargement inutile.
- **Cas "aucune task créée"** : le store n'est alimenté que si `created > 0`, les cas `alreadyExisted` ne déclenchent pas d'auto-sélection.
- **Régression Bug B** : le try/catch ne masque rien de critique, l'interface se débloque simplement à `"idle"` sans afficher l'issue. Pas de changement de comportement sur les chemins normaux (fetch réussi).
- **Création via `createGroupTasks()`** : cette fonction passe par `createTasksForIssues()` — le setter de store s'y appliquera aussi automatiquement.
- **Vérifier que `$planModeTask` s'active** : après `selectTask()`, `selected` est défini et `selectedPanel === "plan"`, donc `planModeTask` est set → `AgentInput` s'affiche → `loadContext()` démarre automatiquement. C'est le comportement attendu pour "la task devrait se charger dès que possible".
